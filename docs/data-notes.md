# Reference dataset notes

## What this is
`src/main/resources/reference-packages.csv` — the 5,000 most-downloaded unscoped
npm packages, with weekly download counts. This is the "known good" set that
newly published packages are matched against for typosquat detection.

Generated by `tools/fetch-reference-packages.mjs`.

## Sources
- `registry.npmjs.org/-/v1/search` — candidate names, ranked by popularity
- `registry.npmjs.org/{pkg}/latest` — package metadata, used for dependency mining
- `api.npmjs.org/downloads/point/last-week` — real weekly download counts

## Method
No npm endpoint exposes a "top N packages" list, so the set is assembled:

1. **Keyword search** across 150 seed terms covering the major areas of the
   ecosystem, three pages deep each. Yielded 51,195 unique unscoped names.
2. **Dependency mining** — the 400 most popular discovered packages are queried
   for their `dependencies` and `peerDependencies`. Yielded 585 names, 273 of
   them not already in the pool.
3. **An explicit `MUST_INCLUDE` list** of known high-value squat targets.
4. Real download counts fetched for all 51,468 candidates (50,938 returned a
   count), sorted, top 5,000 kept.

### Why steps 2 and 3 exist
Keyword search alone recovered only 18 of a 30-package sample of known
high-value squat targets — a 40% miss rate. Missing names included lodash,
jquery, mongoose, passport, uuid, and bcrypt.

The cause is structural, not incidental. npm search matches topic keywords
against a package's name, description, and keywords. Packages whose identity is
a brand name rather than a description of function ("lodash", not "utility
library") do not rank for topic queries and never appear in the result window.
These are also, unsurprisingly, the packages most worth impersonating.

Dependency mining attacks this from the opposite direction: it finds packages by
who depends on them rather than how they describe themselves. Its incremental
yield here was modest (273 new names), and because `MUST_INCLUDE` covers the
same known gaps, the two fixes cannot be individually attributed from this run.
Dependency mining is retained because it is the generalising fix — `MUST_INCLUDE`
only patches gaps already known.

## Coverage
- Most downloaded: `semver`, 832,321,560/week
- Least downloaded: `jest-specific-snapshot`, 308,904/week

## Known limitations
1. **Popularity floor.** The reference set bottoms out at ~309k weekly downloads.
   Squats targeting packages below that threshold are undetectable, because the
   legitimate package is not in the reference set to match against.
2. **Scoped packages excluded.** Names like `@babel/core` are skipped — the bulk
   downloads API cannot batch them. Squats targeting scoped packages are not
   detected in v1.
3. **Discovery is not provably complete.** Keyword search plus dependency mining
   covers the sampled gaps, but coverage cannot be guaranteed. A production
   system would build the reference set from the registry replication feed,
   which enumerates every package rather than sampling.
4. **Point-in-time snapshot.** Counts captured once. Popularity shifts; a real
   system would refresh on a schedule.
5. **Downloads are a noisy popularity proxy.** CI pipelines and registry mirrors
   inflate counts, so this measures automated installs as much as human adoption.
